# Platform Data Closure Audit Runbook

## Purpose

Use this read-only audit before starting a new data campaign. It reviews existing repository data assets and the local Prisma database, then produces a single closure report across school, essay, deadline, profile, case, AI memory, notification, operations, security, benchmark, and governance data.

The audit does not write facts to the database. It only writes a JSON report.

## Command

```bash
pnpm --filter api audit:platform-data-closure
```

write `status: "BLOCKED"`, `summary.blocker.kind:

without an output file. Treat these artifacts as audit availability evidence,

`audit:database-schema-compatibility` is the first follow-up when the platform audit reports `database_audit_availability` or `database_schema_compatibility`. It is read-only: it parses `prisma/schema.prisma`, reads `information_schema` and `_prisma_migrations`, and emits missing table, missing column, unapplied repo migration, applied-migration-missing-from-repo, and extra DB-object rows. Treat `status: BLOCKED` as a P0 blocker; do not run downstream DB-backed worklists as if data domains were closed until this report is `PASS` or every row has an explicit review/terminal disposition.

When these DB follow-up artifacts are available outside `scripts/closure-reports`, pass them back into `audit:platform-data-closure` with the `--schema-worklist`, `--database-schema-disposition`, `--database-schema-operator-handoff`, `--migration-reconciliation`, `--restore-candidate-bundle`, `--checksum-review`, `--checksum-variant-analysis`, `--unrecoverable-artifact-search`, `--local-artifact-search`, `--external-artifact-packet`, `--baseline-resolution`, `--baseline-scope-preflight`, `--backup-evidence-packet`, `--baseline-approval-request`, and `--baseline-proposal` arguments. The platform audit will keep the DB blocker open but include each artifact status and summary in the `database_schema_compatibility` evidence so the top campaign is explainable from the main closure report. For baseline-resolution artifacts, the main blocker includes decision, unresolved mismatch count, exact-match count, missing required operator inputs, approval readiness, and whether the artifact permits DB writes. If `baseline-scope-preflight` still reports `BLOCKED_BACKUP_EVIDENCE_REQUIRED` but a paired backup evidence packet reports `REVIEW_BACKUP_OR_DISPOSABLE_TARGET_READY` or otherwise has zero missing required inputs, the platform audit keeps the preflight as evidence but does not count it as a separate release blocker.

`audit:database-schema-disposition` consumes the schema worklist plus alignment/reconciliation/restore/baseline evidence and maps every schema drift row to an explicit block-release, review, or conflict disposition. Missing tables and unapplied repo migrations stay `block_release` until an approved operator workflow aligns the database; checksum-matched missing migration files become restore-candidate review rows; unrecoverable migration history becomes external-artifact or baseline-review conflict; extra DB objects become review-only schema drift rows. The packet is read-only, writes JSON/Markdown/CSV, and never runs Prisma migrate, resolve, db push, SQL restore, or pg_restore.

`audit:database-schema-operator-handoff` consumes the schema disposition plus recovery artifacts and turns them into an ordered operator handoff. It groups rows into restore-candidate review, unrecoverable migration recovery/baseline review, extra DB object review, and current repo migration apply phases. The packet is read-only and intentionally omits runnable DB-write commands; it exists so the remaining block-release path is explicit without asking Codex to run Prisma migrate, resolve, db push, SQL restore, or pg_restore.

`audit:database-schema-alignment-plan` consumes the schema compatibility worklist and turns it into a read-only operator plan. It maps missing tables/columns back to unapplied migration SQL where possible, flags divergent migration history, writes JSON plus Markdown, and explicitly sets `destructiveDbWriteAllowedByThisPlan: false`. If the plan reports `BLOCKED_DIVERGENT_MIGRATION_HISTORY`, restore/review missing migration files or document a baseline/resolve decision before applying migrations to any valuable database.

`audit:database-migration-history-reconciliation` is the next read-only follow-up for `applied_migration_missing_from_repo` rows. It checks whether each DB-applied migration can be recovered from local git history, compares recovered SQL SHA-256 to the `_prisma_migrations.checksum` captured by the schema worklist, and emits restore-or-baseline-review rows. It never restores files automatically; recovered migrations still require an explicit operator decision because the current repo may intentionally contain a squashed `0001_baseline`.

`audit:database-migration-restore-candidate-bundle` consumes reconciliation output and stages only checksum-matched recovered migration SQL into a review bundle outside `prisma/migrations`. It is useful when most missing history is recoverable but one row is still blocked: reviewers can inspect the good candidates while exact-SQL recovery continues. The bundle never writes to the actual migration directory and never approves a DB write.

`audit:database-migration-checksum-review` is the final read-only follow-up for checksum mismatch rows. It records the search scope for exact SQL recovery across the current workspace, path-specific git history, stashes, and optionally unreachable git blobs with `--include-unreachable`. If it reports `BLOCKED_EXACT_SQL_NOT_FOUND`, the next step is an external artifact/backup lookup or an explicit baseline/resolve decision; do not apply migrations to valuable data while this remains unresolved.

`audit:database-migration-checksum-variant-analysis` consumes the checksum review and tests deterministic text variants of the recovered SQL candidates: line-ending normalization, final-newline normalization, BOM toggles, trailing-whitespace trimming, leading SQL comment stripping, line-comment stripping, and blank-line collapse. It is read-only and does not claim a variant is safe to restore automatically. A `BLOCKED_NO_VARIANT_MATCH` result means common text-normalization explanations are exhausted and the remaining path is external exact-SQL recovery or an explicit non-production baseline/resolve decision.

`audit:database-migration-unrecoverable-artifact-search` consumes migration-history reconciliation rows whose disposition is `unrecoverable`. It hashes candidate `migration.sql`/`.sql` files and optional archive entries against the DB `_prisma_migrations.checksum`, with a path filter centered on the migration name unless `--scan-repo-sql` widens repository SQL scanning. It is read-only and does not copy artifacts, restore migrations, or approve baseline decisions. A no-match result is evidence for an external deployment/backup/team-clone request or non-production baseline review.

`audit:database-migration-local-artifact-search` is a controlled local search for an exact migration SQL artifact. It reads only files named `migration.sql` or `.sql` files whose path includes the target migration name, under the configured candidate roots. By default it searches the repo, Desktop, and Downloads; add `--candidate-root <dir>` for recovered backup folders. It writes JSON/Markdown evidence and never writes to Prisma migrations or the DB.

`audit:database-migration-external-artifact-packet` turns `BLOCKED_EXACT_SQL_NOT_FOUND` into an operator handoff packet. It scans local candidate roots for an exact SHA-256 artifact, summarizes the unresolved migration, and emits a copyable request for deployment artifacts, backups, or teammate clones. Use `--candidate-root <dir>` to scan recovered artifacts dropped into a local directory, `--scan-repo-sql` when you want an additional repository-wide `.sql` scan, and `--scan-archives` to inspect matching SQL entries inside `.zip`, `.tar`, `.tgz`, `.tar.gz`, and `.gz` archives without extracting files to disk. If the blocker is an unrecoverable DB-applied migration rather than a checksum-review mismatch row, pass `--migration <name>` and `--target-sha256 <db-checksum>` so the packet and platform audit request the exact current artifact instead of a stale checksum-review target. This packet is read-only and does not approve DB writes.

`audit:database-migration-baseline-resolution` is the read-only decision gate after exact SQL recovery has been exhausted. By default it reports `BLOCKED_DECISION_REQUIRED` and allows no DB writes. Pass `--external-artifact-packet` whenever an external lookup packet exists; exact SQL matches found in that packet count as reviewable evidence for `--decision restore-exact-sql`, without first copying the file into the repo or checksum-review report. The script emits a machine-readable `summary`, `requiredOperatorInputs`, `operatorGuardrails`, and `recommendedNextStep` so the platform audit and operator handoff can distinguish missing approval evidence from an approved exact-SQL restore review or local/staging baseline review artifact. It can generate a review artifact for `--decision baseline-resolve-local-only` only when the operator provides a supported non-production target scope, an approved workflow ID, the exact `APPROVED_DATABASE_MIGRATION_BASELINE_RESOLVE` acknowledgement, rationale, and backup/clone evidence. It never runs `prisma migrate resolve`, `migrate deploy`, `db push`, or any destructive command.

`audit:database-migration-baseline-scope-preflight` is a read-only target-scope preflight for the baseline path. It fingerprints the current database through `pg_catalog` and `information_schema`, redacts credentials, infers whether the target is local/staging/unsupported, checks for production-like host or database signals, and records whether backup/disposable/staging-clone evidence is present. It does not approve a baseline, does not dump data, and does not run Prisma resolve/deploy.

`audit:database-migration-backup-evidence` is the read-only evidence packet between scope preflight and baseline approval. It can verify metadata for a supplied `--backup-artifact` file, or carry explicit `--backup-evidence`, `--disposable-target-evidence`, or `--staging-clone-evidence` text into a machine-readable artifact. It never runs `pg_dump`, never approves the baseline, and never grants permission to run Prisma writes. A `REVIEW_BACKUP_OR_DISPOSABLE_TARGET_READY` packet can be used only as input to `audit:database-migration-baseline-resolution`.

If an operator creates a local backup artifact for this packet, store it outside the repo, treat it as sensitive, and keep only metadata in closure reports. Prisma-style URLs may include `?schema=public`, which `pg_dump` does not accept as a libpq URI query parameter; strip that query parameter before running `pg_dump`. A successful local backup evidence packet should record `backupArtifactExists=true`, a SHA-256 hash, size, target scope, and `readyForBaselineResolutionInput=true`.

`audit:database-migration-baseline-approval-request` is the read-only handoff after backup evidence exists but before approval. It verifies that exact-SQL recovery is exhausted, target scope is local/staging-cleared, backup evidence is ready, and the only remaining baseline-resolution inputs are the approved operator workflow ID plus exact `APPROVED_DATABASE_MIGRATION_BASELINE_RESOLVE` acknowledgement. It emits an audit-only command template; it does not approve the decision and still omits Prisma write commands.

`audit:database-migration-baseline-proposal` consolidates the schema worklist, migration reconciliation, restore bundle, checksum review, checksum variant analysis, unrecoverable artifact search, local artifact search, external artifact packet, baseline resolution gate, baseline scope preflight, backup evidence packet, and baseline approval request into one operator-facing proposal packet. It carries open migration-history rows, including checksum-matched restore candidates and unrecoverable DB-applied migrations, so it must not report pass merely because checksum mismatches are zero. It can distinguish exact-SQL review, approved exact-SQL restore review, backup-evidence readiness, approval-request readiness, and approved non-production baseline-resolution review states. It is useful when exact SQL recovery is exhausted and the remaining decision is external artifact handoff or explicit non-production baseline/resolve approval. The script is still read-only: it does not approve the decision, does not restore migration files, and intentionally omits DB-write command templates.

A `candidate_validated_for_review` row is still not trusted data: it only means fetched page text matched prompt snippets closely enough for reviewer/staging follow-up. The platform audit can consume it with `--ai-memory-disposition`; a ready packet makes chat/application-analysis memory context explicitly weak-state aware without allowing memory-derived facts to override sourced school, deadline, essay, or prediction data.

The package can be consumed through the read-only admin endpoint:

```bash
GET /admin/profile-readiness/delivery-package?queue=user_prompt&severity=critical&page=1&pageSize=50
```

The endpoint requires an operator with `DATA_HEALTH`, reads the latest `profile-readiness-admin-delivery-*.json` file from `apps/api/scripts/closure-reports`, and never writes notifications or profile data. It rejects any package whose privacy metadata says `includesUserIds: true`; direct outreach with raw user IDs still requires a separate approved operator workflow.

Raw user ID exports are guarded and private-only. If a human operator workflow is explicitly approved, generate that package outside the default admin surface:

```bash
pnpm --filter api audit:profile-readiness-admin-delivery -- \
  --worklist /tmp/profile-readiness-worklist.json \
  --policy scripts/data/profile-readiness-delivery-policy.json \
  --include-user-ids \
  --approved-operator-workflow <approved-workflow-id> \
  --operator-ack APPROVED_PROFILE_READINESS_RAW_USER_ID_EXPORT \
  --out scripts/closure-reports/private/profile-readiness-admin-delivery-raw.json \
  --csv scripts/closure-reports/private/profile-readiness-admin-delivery-raw.csv
```

The script refuses raw user ID output without the workflow ID, exact acknowledgement phrase, and `scripts/closure-reports/private/` destination. That private directory is ignored by Git, and the `DATA_HEALTH` endpoint still rejects raw-ID packages.

`audit:profile-readiness-live-delivery-gate` reads the latest admin delivery package, the delivery policy, Prisma schema, notification controller/service, and shared routes. It emits a read-only gate report that explains whether Redis feed, remote push, and email readiness nudges are eligible for live delivery. The platform now has a `UserNotificationPreference` model, `GET/POST /notifications/preferences`, shared routes, and a read-only delivery-service consent helper that joins readiness preferences with valid Redis Expo push-token presence. Live delivery remains blocked until policy opt-in and a non-default approved recipient workflow exist.

In the platform audit, live delivery blockers that are intentionally caused by the approved no-send/default-anonymous posture, such as `channel_disabled_by_policy` and `recipient_user_ids_redacted`, are treated as review-only evidence once the live-delivery gate exists. Missing infrastructure, missing consent joins, missing preference APIs, or absent gate reports remain blockers.

Default inputs:

- `apps/api/scripts/data`
- `apps/api/scripts/cds-data`
- `apps/api/scripts/closure-reports`
- Prisma database from `DATABASE_URL`
- the platform data SOP/ADR/matrix docs listed in the report

## How To Read The Report

Each domain has the same review shape:

- `coverage`: how much data exists
- `freshness`: whether the data is stale for that domain
- `sourceQuality`: whether data comes from official, secondary, UGC, heuristic, or unknown sources
- `provenance`: whether source URL, evidence, confidence, review, and year signals exist
- `conflicts`: known disagreement or unsafe-state proxies
- `consumerClosure`: whether a real product surface can consume the data safely
- `nextAction`: `accept`, `review`, `refresh`, `backfill`, `mark-terminal`, or `block-release`

The report also includes `topCampaigns`. Work those in order unless the user explicitly changes priorities.

If the Prisma database is attempted but unavailable, the report must include a P0 `database_audit_availability` domain with `nextAction: block-release`. If the database connects but current Prisma queries fail because migrations/schema are behind, the report must include P0 `database_schema_compatibility` with `nextAction: block-release`. Treat both as closure blockers, not as successful file-only audits. Use `--no-db` only when you intentionally want repository-file inventory; a no-DB report cannot close any DB-backed P0/P1 domain.

For a closed-loop pass, run the platform audit first, then run the worklist matching the top campaign. A worklist row is actionable only when it has one of these dispositions:

- `accept`: already safe to leave alone
- user/action prompt: first-party data must be collected from the user
- source/review action: existing candidate evidence needs Codex or human review
- generation action: downstream consumer rows can be generated from trusted upstream data
- terminal/conflict action: do not write a value until the terminal or conflict decision is explicit

## Closure Rule

A data domain is not closed just because it has rows. It is closed when:

- critical rows are sourced or explicitly terminal
- stale and conflicting rows are routed to review
- missing provenance is fixed or accepted as internal first-party data
- relevant consumers can render weak states safely
- the next audit no longer lists a blocker for that domain

Cases and prediction feedback remain diagnostic-only under ADR-0020. They must not auto-train or auto-calibrate prediction.
