# 多端留学申请辅助平台 UI 语言研究框架

> **文档类型**：研究框架 + 产品落地指南（非已发表实证结论）  
> **设计基线**：[`DESIGN_SYSTEM.md`](./DESIGN_SYSTEM.md) v2.1 — Academic Professional（学术严肃风）  
> **状态**：v0.2 草案（供 Phase 1 审计与评审迭代）  
> **最后更新**：2026-04-19

## 1. 摘要

在数字化转型背景下，教育科技正从「信息展示」转向「高阶决策支持」。**留学申请**属于典型 **高决策成本、强焦虑、对信任极度敏感** 的场景：界面不仅是功能载体，更是**信任信号、认知减负与专业主义**的媒介。

本仓库产品为 **AI 驱动的智能留学申请辅助平台**（选校推荐、录取预测、案例分析、文书与 Agent 能力等），技术形态为 **Next.js Web + Expo 移动端 + NestJS API**，并具备 **中/英国际化** 与较复杂的功能面（仪表盘、预测、学校、组队招募、社区等）。

本文档在 **不替代** `DESIGN_SYSTEM.md` 的前提下，完成三件事：

1. **问题界定**：把「整体 UI 语言」拆为可研究子问题（AI 可信度、多端隐喻、i18n 排版、效率与情绪支持）。
2. **证据分级**：区分 **文献/行业共识**、**设计假设**、**待验证结论**，避免把主张写成已证事实。
3. **落地路径**：三阶段研究流程 + **分层 UI 规范 v0.1**（与 v2.1 **自洽**：营销层不默认引入 DS 已禁止的渐变/发光阴影；若需突破，必须走「实验 → 评审 → 修订 DS」）。
4. **对标库**：§8 汇总可对照的业界模式（**第三方商标与界面版权归各权利人**；此处仅作研究与模式抽象，不代表背书或照搬）。

## 2. 研究对象与边界

### 2.1 产品与技术边界

| 维度         | 说明                                                                                                                                                               |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 核心用户任务 | 选校调研、录取预测、材料与文书、进度与协作、社区/组队等                                                                                                            |
| Web          | `apps/web`，路由与功能面多，深度分析、对比、过滤为主                                                                                                               |
| Mobile       | `apps/mobile`（Expo），碎片查询、通知驱动、触控与单手场景为主                                                                                                      |
| 其他触点     | 浏览器扩展等嵌入式场景：宜极简提示，避免干扰主站流程                                                                                                               |
| 国际化       | Web `next-intl` / 移动端 i18n；中英文案长度与排版差异显著                                                                                                          |
| 共享契约     | `packages/shared` 以类型与 API 契约为主；**视觉语义的一致性**建议通过独立 **Design Tokens / 文档映射表** 维护单一事实来源（见 §6.3），不必与业务类型混放在同一包内 |

### 2.2 设计系统基线（不可默认违背）

v2.1 核心取向（详见 `DESIGN_SYSTEM.md`）：

- **边框优先**：层级用实体边框，而非发光阴影。
- **克制色彩**：现代蓝主色 + 受控语义色（录取/拒绝/候补等）；禁止典型「AI 感」蓝青渐变与发光阴影类用法。
- **小圆角、克制动效**：圆角与阴影以文档与 `globals.css` token 为准。
- **排版 token 化**：营销/应用字号走既定阶梯（如 `text-display`、`text-title` 等），避免魔法数字。

**本研究文档中的「分层规范」= 在 v2.1 允许空间内的强度分级**；任何「放宽到渐变/强发光」仅可作为 **对照实验稿**，默认 **不得** 合并入主分支规范，除非修订 DS 并记录 ADR。

## 4. 理论框架与主张分级

### 4.1 文献与行业共识（需补引用或标注来源）

以下适合作为文献综述素材；正式论文/对外材料中应 **补参考文献** 或改为弱表述「常见实践认为…」：

- **高 stakes 场景**下，用户优先评估合法性、胜任力与透明度；界面元素作为 **信任信号** 被广泛讨论（金融、医疗、政府数字服务等领域的 HCI 文献与指南）。
- **Calm Technology** 强调技术多数时间在注意力外围，必要时再进入中心；适用于高焦虑、高打断环境（需引用 Weiser 等原始与后续综述）。
- **渐进式披露**、容错与可撤销、非遮挡式进度反馈等，属于降低认知负荷的常规模式（Nielsen 启发式等）。

### 4.2 本项目设计假设（待 Phase 2 验证）

- **H-AI-1**：仅展示点估计概率而不展示 **局限与依据**，会降低长期信任；**适度坦诚不确定性** 可提升主观信任（需对照实验）。
- **H-AI-2**：「解释性 UI」（要点级依据、溯源入口）比单纯美化视觉更能改善 AI 模块的可理解性。
- **H-EMO-1**：敏感结果页增加 **受控留白**（如容器内边距在 token 阶梯内上调一档）与 **引导性微文案**，可改善情绪自评且不显著损害专家用户效率（需分层样本）。
- **H-LAYER-1**：**营销层 / 工具层 / AI 洞察层** 三级强度可在不违背 v2.1 禁止项的前提下提升整体一致性（见 §7）。

## 5. 分主题设计要点（与仓库实现对应）

### 5.1 AI 预测与建议：从黑盒输出到可协作

**目标**：在遵守 v2.1 的前提下，用 **结构与文案** 建立可信度，而非用渐变与发光「炫技」。

建议 UI 模式（可与现有页面对照审计）：

| 模式              | 说明                                                                        |
| ----------------- | --------------------------------------------------------------------------- |
| 不确定性表达      | 点估计 + 定性带宽或数据充足度标签（具体文案与统计定义需产品与数据团队对齐） |
| 依据摘要          | 「为何如此建议」要点列表（非长篇论文），可链接到详情                        |
| 溯源/数据脉络     | 关键输入维度与参考数据范围的可读摘要（注意隐私与误导风险，需法务/产品审核） |
| Human-in-the-loop | 显式反馈、修正输入、保存「我的假设」等，让用户感知主导权                    |

### 5.2 任务效率 vs. 情绪支持

- **工具页**：优先可扫描表格、过滤与批量操作；遵守网格与边框层级。
- **敏感结果/失败态**：在 token 体系内增加 **情绪缓冲**（略增间距、分段标题、下一步明确 CTA）；微文案从 **指责型** 转为 **引导型**（例：「补充以下字段可提升预测校准度」）。
- **冷静技术取向**：进度用非遮挡式条带；关键操作提供撤销/自动保存（产品/工程能力允许范围内）。

### 5.3 多端：逻辑隐喻一致，而非屏幕克隆

| 终端   | 交互现实             | UI 语言侧重点                                            |
| ------ | -------------------- | -------------------------------------------------------- |
| Web    | 键鼠、多列、复杂过滤 | 高密度数据、强层级、可对比布局                           |
| Mobile | 触控、碎片、通知     | 概要优先、触控目标尺寸、即时反馈与推送策略（与焦虑相关） |
| 扩展   | 嵌入、轻量           | 极简提示，不抢主任务                                     |

一致性重点：**状态语义色、图标语义、文案术语** 与 DS 一致；导航形态可按平台惯例（侧栏 vs Bottom Tabs）。

### 5.4 国际化与排版（工程与设计交界）

**原则**：承认中/英在行长、词法、基线视觉上的差异；避免「一套魔法行高解决所有脚本」。

建议纳入 Phase 1 审计的具体现象：

- 按钮与标题在 `en` 下溢出、在 `zh` 下过短导致视觉失衡。
- 表格列在某一 locale 下严重折行。
- 语言切换时的 **布局跳动**（CLS）：骨架屏、最小宽度、折行策略是否与 locale 联动。

**实现策略（择优迭代，而非一次到位）**：在 Web 侧可考虑按 `locale` 注入 typography utility 类；移动端对齐同一 token 表。高级方案（如「预测文案宽度」）成本高，仅在有明确数据支持时立项。

### 5.5 竞品与品类对齐（差异化）

对标物应选 **任务结构相近** 的高 stakes 产品（长表单、强合规、重数据），而非仅名称带「留学」的产品。

差异化建议表述为 **「温暖理性」**：**工具与预测** 保持冷峻、精确与边框逻辑；**文书陪伴、社区组队** 可在 **主色点缀、插图、略宽松圆角（仍在 DS token 表内）** 上略增亲和力——作为 **分层** 而非整体换皮。

## 6. 研究方法：三阶段路径与交付物

### 6.1 Phase 1 — 项目内审计（桌面研究 + 走查）

**输入**：`DESIGN_SYSTEM.md`、`FULL_SURFACE_REGISTRY` / 旅程文档（若适用）、关键路由清单（Web `apps/web`、Mobile 核心屏）。

**抽样旅程（可裁剪为 5～8 条）**：

| 旅程                    | 走查重点                                      |
| ----------------------- | --------------------------------------------- |
| 首页获客 → 注册/登录    | 营销叙事与 v2.1 底色；错误态语气              |
| 学校搜索 → 详情         | 信息密度与移动端溢出；长文案折行              |
| 发起预测 → 结果         | 数字单薄感；免责声明与局限性；是否「像黑盒」  |
| 文书 / Agent 相关关键屏 | AI 区块与正文区隔；加载与流式反馈是否「沉着」 |
| 组队 / 社区（若已上线） | 社交亲和力 vs. 学术严肃边界                   |
| Mobile 进度与通知       | 与 Web 状态语义一致；空状态路径               |

**交付物**：

- `违规点清单`（与 DS 冲突的组件/第三方样式）
- `高风险模块清单`（预测、支付/订阅若存在、隐私与免责声明展示）
- `i18n 布局风险清单`（页面级截图 + locale 对比）

**建议周期**：可与团队并行；目标为「可勾选的表格」，而非散文。

### 6.2 Phase 2 — 对照实验（固定 IA，变视觉强度）

**控制变量**：同一信息架构、同一文案事实层级；仅变 **密度、圆角档位（仍在 DS 表内）、AI 区块背景（极浅中性色）、插图有无、微动效强度**。

**示例方案（不与 v2.1 冲突）**：

- **方案 A（超理性）**：表格主导、最细边框、无插图。
- **方案 B（温暖理性）**：在 token 内略增内边距与 `rounded-lg`/`rounded-xl` 使用比例、品牌色 **点缀**、仅允许 DS 允许的 `shadow-card` / `shadow-elevated`。
- **方案 C（结构化 AI）**：AI 建议置于 **浅中性底 + 边框** 容器，强调依据与反馈入口；仍禁止发光渐变。

**方法**：5 秒第一印象 + 简短任务信心量表（5～7 题）+ 可选简易任务（如「找到预测依据」）。

**交付物**：原始分数、图表、结论陈述（**显著性/样本量**若不足则明确写为探索性）。

### 6.3 Phase 3 — 收敛为「一套主语言 + 分层规范」

**交付物**：

- `UI 语言分层规范 v0.1`（即 §7，修订入下一版或独立附录）
- 与 `DESIGN_SYSTEM.md` 的 **diff 列表**：哪些进入主 DS，哪些仅作「页面级模式」
- 可选：`ADR` 记录重大视觉原则变更

**单一事实来源（推荐工程组织）**：

- 文档层：状态 → 颜色/token 映射表（中英文名称一致）。
- 代码层：独立 tokens 包或 CSS 变量管道，由 Web / RN 消费；**不必**将设计 token 与 `packages/shared` 业务类型混绑。

## 7. UI 语言分层规范 v0.1（与 v2.1 自洽）

三层定义：**营销层（叙事）**、**工具层（功能）**、**AI 洞察层（解释）**。下列 **默认遵守** `DESIGN_SYSTEM.md`；阴影仅使用文档允许的 token，**禁止** DS 已列明的发光/渐变套路。

### 7.1 分层总览

| 维度         | 营销层（Marketing）                                                                                         | 工具层（Tooling）                     | AI 洞察层（AI Insight）                                            |
| ------------ | ----------------------------------------------------------------------------------------------------------- | ------------------------------------- | ------------------------------------------------------------------ |
| **目标**     | 建立品牌与信任入口，引导注册                                                                                | 高效率完成专业任务                    | 解释 AI 输出、降低黑盒感                                           |
| **信息密度** | 中低，叙事与证据并排                                                                                        | 中高，表格与过滤为主                  | 中，分组+要点+可选展开                                             |
| **圆角**     | 可用 `rounded-lg`～`rounded-xl`（卡片/区块）                                                                | 默认 `rounded-sm`～`rounded-md` 为主  | `rounded-md`～`rounded-lg` 容器区分                                |
| **背景**     | 允许大面积 **纯色** 品牌底（注意对比度）；可用 **低对比几何纹理/摄影**（需无障碍审查）；**不默认** 多色渐变 | 白/中性表面，边框分栏                 | **极浅中性底**（如 `gray-50` 级，以 token 为准）+ 边框，与正文区分 |
| **边框**     | 1px 浅中性或无边（大色块需替代层级手段）                                                                    | **2px / 强分区** 优先（与 DS 一致）   | 1px～2px；可对「依据」块用虚线以示引用/补充                        |
| **阴影**     | 仅允许 **DS 标准** 的轻阴影（如悬浮卡片）；禁止发光                                                         | 默认扁平+边框；悬浮用 `shadow-card`   | 可用 **一级 elevation** 表达可交互卡片，仍避免喧宾夺主             |
| **动效**     | 入场可略长，须尊重 `prefers-reduced-motion`                                                                 | 短转场（如 150ms 量级）、状态反馈为主 | 展开/折叠、骨架与流式更新；避免闪烁式强调                          |
| **文案语气** | 可信、克制激励，避免夸大录取承诺                                                                            | 简练、客观、可扫描                    | 解释性、透明、邀请校对                                             |

### 7.2 与旧版「附录表」的差异说明（重要）

此前草案中「营销层渐变背景、Elevation 2 叙事长动画」等表述 **易与 v2.1 冲突**。本 v0.1 表已改为：

- 用 **纯色/摄影/低对比纹理** 替代「渐变」作为默认营销手段；渐变仅可作为 **实验分支** 并单独立项评审。
- 阴影 **严格落在 DS 允许集合**，不引入发光类 shadow。
- 动效强度以 **可访问性与 DS** 为硬约束。

## 8. 对标案例与 UI 模式库（落地参考）

本节将「学术严肃风 + AI 高决策场景」落实为 **可对照的界面模式**；每条均标注与 v2.1 的关系。**证据级别**：多为 **行业实践归纳 + 本项目可检验假设（H）**，非本产品实测结论。

### 8.1 信任感与 AI 解释性：从「黑盒」到「透明」

高决策场景下，**缺少语境的精确数字**容易触发不信任；界面宜把「不确定性」与「依据结构」说清楚。

| 参考                                             | 可抽象模式                                                                                               | 与 v2.1 对齐的落地方式                                                                                          | 备注                                                 |
| ------------------------------------------------ | -------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| **CollegeVine** 类：以 **定性档位** 替代裸百分比 | 用 **Hard Reach / Reach / Target / Likely** 等阶梯标签表达录取难度，而非单独突出「87.5%」                | 档位文案、定义与 **免责声明** 须产品/法务/数据一致；视觉上用 **边框 + 语义色 token**，避免营销式渐变            | 若后端仍存连续概率，前端是 **呈现策略** 而非篡改模型 |
| **IBM Carbon for AI** 类：**可展开的 AI 披露**   | Popover / 抽屉内结构化展示 **Inputs（依据）**、**Confidence（高/中/低）**、**Limitations（未考虑因素）** | **禁止** 采用「带光晕的 AI 角标」（与 v2.1 反发光一致）。改用：**细边框标签、浅色底块、outline 图标**，点击展开 | 与 §5.1「解释性 UI」一致                             |

**落地到本仓库（假设）**：

- **H-EXP-1**：在录取预测/选校理由区块提供 **「查看模型依据」** 入口，默认折叠，展开后为 **要点列表**（可链接到更长说明），可提升「专业感」主观分（Phase 2 验证）。
- 定性说明可配 **一行溯源文案**（示例结构）：_「基于与您背景相近的样本在 GPA、课程与活动维度上的分布对比」_——具体措辞须与真实数据口径一致。

### 8.2 焦虑缓解与冷静技术：高压环境下的 UX

| 参考                                    | 可抽象模式                                                              | 与 v2.1 对齐的落地方式                                                                                                                                       | 风险与假设                                                                                                               |
| --------------------------------------- | ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------ |
| **Apple Health** 类：**视觉聚焦**       | 弱化非当前任务层级，突出「此刻最紧急」的一条线（截止、待补材料）        | **磨砂模糊（frosted blur）** 对部分用户与 **「减少透明度」** 系统设置不友好；默认更稳妥的是 **边框分区 + 留白 + 标题层级**，模糊仅作 **可选实验** 并测无障碍 | **H-CALM-1**：Dashboard 用 **极低对比噪点/纸张纹理** 替代纯平白底，可减轻「医用冷感」（需 Phase 2 对比偏好与对比度审计） |
| **Refera** 等医疗表单类：**渐进式披露** | 依用户已选条件 **分步展示** 字段区块（如先选专业方向，再展开竞赛/科研） | 与 v2.1 不冲突；工程上对齐表单状态机与校验顺序                                                                                                               | 与 §5.2、§4.1 渐进披露共识一致                                                                                           |

**落地到本仓库**：申请偏好、背景信息、选校筛选等长表单，优先 **分段 + 保存进度 + 条件字段**，避免首屏「输入墙」。

### 8.3 多端一致性与工程对标

| 参考                                                 | 可抽象模式                                                             | 落地建议（与 §2.1 / §6.3 一致）                                                                                                                                |
| ---------------------------------------------------- | ---------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Shopify Polaris** 类：**Pro 向中性色与靛蓝工具调** | 管理端主色从「营销绿」转向更 **稳重** 的工具色，跨端传达「稳定、诚实」 | 本仓库 **主色与语义色以 `DESIGN_SYSTEM.md` 为准**；若研究归纳「靛蓝工具感」，应通过 **token 评审** 合并，而非在 `packages/shared` 内硬编码颜色常量混用业务类型 |
| **Status 语义单一事实来源**                          | `Success` / `Warning` / `AI` 等在 Web 与 RN **同名同义**               | 建议 **Status → CSS 变量 / RN theme** 映射表（独立 tokens 包或文档 + 双端实现），与 `packages/shared` **类型契约分离**                                         |
| **React Native** 类：**长文案 CTA 不自撑破版**       | `flexShrink`、`numberOfLines`、省略号策略                              | **Web**：关键 CTA 设 **min-width**、或主次按钮拆行；语言切换时用 **骨架/占位最小高度** 缓解 CLS（见 §5.4）                                                     |

**注意**：文中「AI = 靛蓝**带微光**」与 v2.1 **冲突**；若强调 AI 区块，应采用 DS 已允许的 **紫罗兰/靛蓝系功能色 + 边框/浅底**，**不用发光 shadow**。

### 8.4 视觉层级分级（Layering）：营销 vs 工具 vs 社区

**原则**：工具内页不应像广告页；社区可有温度，但仍宜 **结构化** 而非纯娱乐化流式聊天默认态。

| 区域                 | 可参考对标（模式抽象）                       | UI 核心特征（与 §7 一致）                                        |
| -------------------- | -------------------------------------------- | ---------------------------------------------------------------- |
| **营销 / 首页**      | **ApplyBoard** 类：机构背书、Logo 墙、大字阶 | 社交证明、摄影/纯色大块、仍避免 DS **禁用** 渐变与发光           |
| **Dashboard / 工具** | **Notion / Linear** 类：工作台密度           | 细边框、去装饰阴影、单色图标、灰阶导航                           |
| **社区 / Teams**     | **Piazza** 类：课程问答结构                  | **Q&A / 主题帖** 优于默认 Discord 式无限流；与「学术严肃」更相容 |

**研究用法（密度对比）**：

- **ApplyBoard**：可作 **营销层** 参考——信任背书、强 CTA、叙事密度。
- **Common App**：可作 **工具层** 参考——流程线性、灰阶、克制装饰、表单栅格（与 v2.1 工具取向接近）。

### 8.5 小结：v2.1 下的三条具体路径

在 Academic Professional v2.1 基线下，优先落地的句式是：

1. **用中性色与边框克制情绪**，用 **语义色表达状态**，避免喧闹装饰。
2. **用结构化组件解释 AI**（依据 / 置信 / 局限），**不用光晕渐变「像 AI」**。
3. **用渐进式披露与进度可见性** 缓解焦虑，而非用强动效抢夺注意。

## 9. 未来迭代方向（非承诺路线图）

- **流式 AI 交互**：在保持「沉着」前提下，设计加载、部分结果、撤销与版本对比的 UI 模式。
- **专注模式（Focus Mode）**：一键隐藏次要导航，仅保留当前任务链（需信息架构配合）。
- **设计系统活化**：Storybook / Figma 与代码 token 同步；CI 层已有 typography 检测，可扩展到「禁用 shadow 模式」等。

## 10. 结论（可检验版）

在 **留学申请** 这一高 stakes 场景中，**整体 UI 的成功**更应被操作化为：用户在关键节点（阅读预测、提交材料、支付/授权若适用）上的 **主观信任、任务信心与错误恢复成本** 是否改善。

**v2.1 Academic Professional** 是当前仓库的合理基线；本框架主张通过 **分层** 与 **解释性 AI UI** 补全「仅克制」可能带来的「僵化感」，但 **不以牺牲 DS 禁止项为代价**。最终规范应以 **Phase 2 证据 + DS/ADR 修订流程** 为准。
