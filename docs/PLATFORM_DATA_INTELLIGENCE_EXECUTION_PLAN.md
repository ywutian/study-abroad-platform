# Platform Data Intelligence Execution Plan

> Goal: use Codex/AI as an intelligent data operations layer, not a one-off field filler.

## Mission

Build a complete, source-backed data operating system for the study-abroad platform. The system should continuously discover missing or weak data, identify trusted sources, extract structured facts, preserve evidence, route uncertain records to review, and publish only data that is useful, traceable, and safe for user-facing AI, prediction, essay, timeline, school, recommendation, chat, and application-analysis surfaces.

## Long-Running Goal Contract

This is a standing goal, not a one-time documentation task. Keep it active until the user explicitly asks to pause, complete, or replace it.

At the start of every future execution pass:

- Re-read this plan and `PLATFORM_DATA_FIELD_MATRIX.md`.
- Check the latest schema, scripts, docs, coverage reports, closure reports, data-health surfaces, and user requests.
- Select the highest-value open campaign from the backlog, prioritizing P0/P1 data that affects prediction, recommendations, essays, deadlines, timelines, chat context, application analysis, and trust-building school pages.
- Run the intelligence loop: inventory, gap detection, source planning, extraction, validation, write/review, publish/consume, and monitor.
- Preserve provenance, evidence, source quality, freshness, conflict status, and terminal status for external facts.
- End each pass with a change summary, remaining gaps, next campaign, and verification result.

Do not mark the goal complete just because one campaign is done. Campaign completion should narrow the backlog and improve the next pass.

Stop only when the platform data closure audit gate is `PASS`, or when every core P0/P1 data domain has an explicit `trusted`, `review`, `terminal`, or `conflict` disposition, no `block-release` rows remain, consumer closure checks are documented, and the user explicitly accepts completion. If any `OPEN`, `REVIEW`, `BACKFILL`, or untriaged campaign remains, continue with the next highest-value campaign.

## Data Domains

The platform data map must cover these domains:

- Applicant profile: GPA, GPA scale, semester history, tests, activities, awards, education, high school, curriculum, nationality, residency, financial aid need, target majors, target schools, application rounds.
- School facts: identities, aliases, rankings, admissions rates, SAT/ACT bands, GPA distribution, CDS admit bands, enrollment, tuition, aid, outcomes, campus life, media, descriptions.
- Application policy: deadlines, ED/EA/RD/REA/Rolling, testing policy, fee waiver, Common App/Coalition, international aid, interview policy, school-specific policy evidence.
- Essay data: Common App, UC PIQ, supplemental prompts, why-school prompts, word limits, required/optional status, yearly changes, source snapshots, prompt audit history, example essays.
- Program and opportunity data: majors, CIP codes, program selectivity, earnings, competitions, summer programs, scholarships, global events, team/recruitment contexts.
- Outcome and case data: admission cases, verified labels, verification proof metadata, public case narratives, essay examples, prediction feedback, swipe outcomes.
- AI and personalization data: agent conversations, memory, entities, graph entities, relationships, user AI preferences, route embeddings, tool traces.
- Governance data: provenance, source observations, closure targets, review statuses, terminal statuses, source quality, freshness, conflicts, license blocks, audit logs.
- Product operations data: notifications, push tokens, points, subscriptions, payments, feature flags, quotas, referrals, bans, reports, moderation.
- Benchmark and model data: benchmark profiles, competitor sources/runs/predictions, static teacher snapshots, distillation aggregates, prediction model registry, policy versions.

## Intelligence Loop

Every data campaign should run through the same loop:

1. Inventory
   - Read schema, docs, routes, frontend consumers, and existing coverage reports.
   - Build the field matrix: data field, owning model, consumer surfaces, source priority, freshness rule, risk if missing.

2. Gap Detection
   - Use coverage scripts, closure reports, admin data-health, and direct DB queries.
   - Classify each field as official, scraped, seed, inferred, stale, missing, terminal, conflicted, or license-blocked.

3. Source Planning
   - Prefer official school pages, CDS, IPEDS/Scorecard, state systems, institutional research, and approved public datasets.
   - Use secondary aggregators only where policy allows and mark them clearly.
   - For UGC data, require privacy, consent, quality scoring, and review status.

4. Extraction
   - Use AI to read PDFs, HTML, CSVs, screenshots, and existing raw scrape records.
   - Extract only structured facts with source snippets, source URLs, cycle year, confidence, and notes.
   - Never let LLM-generated facts skip evidence.

5. Validation
   - Apply field-specific range gates, year gates, source-family rules, duplicate checks, and conflict detection.
   - Compare against existing values and provenance before writing.
   - Route low-confidence or conflicting values to manual review.

6. Write And Review
   - Write values with provenance, evidence, fetchedAt, sourceQuality, reviewStatus, and terminal status where relevant.
   - Keep raw content or source snapshots for audit where the model supports it.
   - Use admin review queues for media, essay prompts, school policy, cases, and suspicious data.

7. Publish And Consume
   - Verify API responses and frontend surfaces after publishing.
   - Confirm prediction, recommendation, profile analysis, essay, timeline, chat context, and school pages consume the updated fields.
   - Show uncertainty and source quality in user-facing explanations where relevant.

8. Monitor
   - Track coverage, freshness, source mix, failed extraction, terminal counts, and user-facing weak states.
   - Re-run stale-field campaigns by cycle year, especially for deadlines, essay prompts, testing policy, admit rates, and aid.

## AI Execution Modes

- Cartographer: maps all fields, consumers, owners, and gaps.
- Researcher: finds source candidates and ranks them by source quality.
- Extractor: converts raw source material into structured candidate facts.
- Skeptic: checks ranges, conflicts, source fit, freshness, and hallucination risk.
- Operator: writes approved data through scripts or admin workflows.
- Auditor: produces closure reports, diff summaries, and user-facing verification checks.

   - notifications, push tokens, subscriptions, feature flags, quotas, audit/security logs, report/moderation queues.

## Source Contract

Every externally sourced field should carry:

- value
- sourceUrl
- sourceName or sourceType
- trustTier
- fetchedAt
- cycleYear or effectiveFrom
- confidence or sourceQuality
- reviewedBy/reviewedAt when reviewed
- rawEvidence or rawContent where feasible
- terminalStatus when no public source exists
- conflictStatus when sources disagree

## Completion Criteria

A data domain is not complete when values merely exist. It is complete when:

- critical fields have coverage targets and freshness thresholds
- missing fields are either actionable or explicitly terminal
- consumer surfaces render the data and weak states correctly
- provenance is visible to admin tools and available to user-facing explanations where appropriate
- tests or scripts prevent silent regressions
- closure reports show no unreviewed blocker rows

The whole long-running goal is not complete until every core data function has either passed its quality gates or has a durable review/terminal/conflict disposition. Partial campaign closure is progress, not a stop condition.
