# Web / Mobile 复用合理性 Rubric

> 目标：不只判断“两个端都有这个功能”，而是判断它们是否在保持业务一致的同时，分别符合各自平台习惯。

## 1. 适用范围

- `A11`
- `SJ-3`
- 所有同时存在于 web 和 mobile 的核心旅程

## 2. 什么叫“复用合理”

复用合理不等于 UI 一模一样，而是同时满足：

- 业务语义一致
- 关键结果一致
- 各端操作路径自然
- 信息层级适应各自屏幕和交互方式
- 没有明显“把另一端硬搬过来”的痕迹

## 3. 五个检查维度

| 维度         | PASS 标准                                | 失败表现                                      |
| ------------ | ---------------------------------------- | --------------------------------------------- |
| 数据语义一致 | 同一指标、状态、未读数、结果含义一致     | web 和 mobile 同名信息含义不同                |
| 信息结构等价 | 关键内容顺序和权重一致                   | 一端缺核心信息或次序完全失衡                  |
| 平台交互自然 | 符合各自平台导航、返回、滚动、点击习惯   | web 逻辑硬塞到 mobile，或 mobile 交互搬到 web |
| 视觉密度合理 | 各端都不挤、不空、不难读                 | mobile 过挤、web 过空、组件比例失衡           |
| 状态同步可靠 | 登录态、已读态、列表刷新、保存结果可对上 | 同一用户跨端状态长期对不上                    |

## 4. 必查功能矩阵

| 功能                 | Web 必查                       | Mobile 必查                              | 允许差异                    | 不可接受                        |
| -------------------- | ------------------------------ | ---------------------------------------- | --------------------------- | ------------------------------- |
| 登录 / 会话          | 登录、退出、恢复               | 登录、冷启动恢复                         | mobile 可多一步权限或启动页 | 一端能登录，一端大量 401        |
| Profile              | 基本信息、分数、活动、奖项     | 基本信息、完成度、编辑入口               | mobile 可以折叠、更分段     | mobile 只是缩水版且丢业务含义   |
| AI                   | 输入、响应、上下文             | 输入、响应、最小可用性                   | mobile 可简化布局           | mobile 只是能发请求但回答不可读 |
| Prediction / Schools | 结果列表、详情、对比语义       | 列表、详情、关键指标                     | mobile 可少二级分析模块     | 指标含义不一致或数据错位        |
| Notifications        | 列表、未读数、mark read/delete | 列表、未读数、mark read/delete/push open | push 行为只在 mobile        | 未读数、已读状态对不上          |
| Timeline             | 结构、日期、任务层次           | 结构、日期、可读性                       | mobile 可采用卡片流         | 日期和优先级语义不一致          |

## 5. 常见“硬复用失败”信号

- mobile 页面像缩小版桌面仪表盘
- 文字、圆环、卡片或统计组件在小屏上重叠
- 使用只适合 hover 的交互
- web 的多列布局直接压到单列，导致节奏失衡
- 只为复用接口名而忽略 mobile 应有的 loading、empty、gesture 反馈

## 6. 状态判定

| 状态      | 含义                                          |
| --------- | --------------------------------------------- |
| `PASS`    | 业务一致且各端都自然                          |
| `ISSUE`   | 业务一致，但一端体验明显不顺或视觉/交互不合理 |
| `BROKEN`  | 核心信息缺失、状态错乱、关键功能跨端不成立    |
| `BLOCKED` | 因设备、权限或环境限制无法完成同版本对照      |

补充规则：

- “功能都在”但 mobile 明显像硬搬 web，至少记 `ISSUE`。
- “视觉不对”也属于正式跨端问题，不是次要备注。

## 7. 证据要求

- web 截图和 mobile 截图各至少一张
- 同一用户、同一功能、同一 build 的结果对照
- 至少一句“复用合理 / 不合理”的明确结论
- 如判 `ISSUE/BROKEN`，要指出是“语义不一致”还是“平台不自然”
