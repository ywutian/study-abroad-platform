# 组队功能 — 企业级符合性分析

基于项目既有企业级标准（CLAUDE.md、学校图片与管理员编辑企业级方案、ADR、AuditLog 与中间件等）对组队相关文档（设计报告 + 实现计划）进行逐项对照，并给出缺口与补充建议。

---

## 一、项目内「企业级」标准摘要

从 [CLAUDE.md](CLAUDE.md) 与 [学校图片与管理员编辑企业级方案.plan.md](.cursor/plans/学校图片与管理员编辑企业级方案.plan.md) 归纳：

| 维度             | 标准要求                                                                                                                                                                                                           |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **请求管线**     | CorrelationId → Timeout → ThrottlerGuard → JwtAuthGuard → RolesGuard → SanitizeInterceptor → SentryInterceptor → TransformInterceptor → LoggingInterceptor → AllExceptionsFilter                                   |
| **响应格式**     | 成功：`{ success, data, meta: { timestamp, correlationId, responseTimeMs } }`；错误：`{ success: false, error: { code, message, timestamp, path, correlationId } }`                                                |
| **错误码**       | BAD_REQUEST, UNAUTHORIZED, FORBIDDEN, NOT_FOUND, CONFLICT, DUPLICATE_ENTRY, RATE_LIMIT_EXCEEDED, INTERNAL_ERROR 等；Prisma P2002→409, P2025→404（[ADR-0006](docs/adr/0006-prisma-exception-handling-strategy.md)） |
| **审计**         | 关键管理员/安全操作调用 `AuditLogService.log({ userId, action, resource, resourceId, metadata })`，不记录完整 body                                                                                                 |
| **缓存**         | 写操作后按需失效（如学校 update 后 `invalidateSchoolCache(id)`）                                                                                                                                                   |
| **DTO 与校验**   | class-validator（@IsUrl、@IsOptional、仅允许 https 等）；SanitizeInterceptor 防 XSS                                                                                                                                |
| **前端路由保护** | middleware 中 PROTECTED_PATTERNS / ADMIN_PATTERNS；未登录重定向 login + callbackUrl                                                                                                                                |
| **i18n**         | 新增能力需 en/zh 全覆盖，key 命名空间（如 admin.schools._, teams._）                                                                                                                                               |
| **测试**         | 新模块需 _.controller.spec.ts、_.service.spec.ts，mock 依赖                                                                                                                                                        |

## 二、组队文档现状与符合性

### 2.1 已覆盖且符合的部分

- **产品与数据模型**：Team / TeamMember / TeamInvitation 划分清晰，与 User、School 关联明确；可见性、加入策略、角色（owner/admin/member）与设计报告一致。
- **前端**：路由与 IA（/teams、/teams/create、/teams/[id]、/teams/[id]/settings、/teams/join?token=）、双 Tab（我的/发现）、Dialog vs 整页、空状态与边界文案、i18n 命名空间 `teams.*` 在设计报告中已明确。
- **用户流与边界**：发现/加入、创建/邀请/管理、我的队伍/离开/解散三条主流程及「队伍已满、邀请失效、未登录、无权限」等边界在设计报告中有表格与文案建议。
- **UI 与设计系统**：PageHeader + PageContainer、TeamCard、EmptyState、toast/AlertDialog、Loading/Skeleton、动效与无障碍在设计 agent 的 UI 报告中有对应建议。

### 2.2 缺口与建议（需写入实现计划或设计文档）

#### （1）认证与鉴权（后端）

- **现状**：设计报告仅描述「未登录可看发现、加入需登录」，未明确各 API 的 JWT / @Public()。
- **企业级要求**：与 [CLAUDE.md 认证与授权](CLAUDE.md) 一致，需在计划中写清：
  - **公开接口**（可 `@Public()`）：`GET /teams`（发现列表，仅返回 PUBLIC 且满足可见性）、`GET /teams/:id`（详情，按 visibility + 是否成员返回不同字段）；`GET /teams/join?token=...` 或 `POST /teams/:id/accept-invite`（校验 token 后可先读再决定是否需登录）。
  - **需 JWT**：`GET /teams/my`、`POST /teams`、`PATCH /teams/:id`、`POST /teams/:id/join`（OPEN 直接加入）、`POST /teams/:id/leave`、`POST /teams/:id/invite`、接受邀请、`DELETE /teams/:id`、成员列表/踢人等。
  - **鉴权**：在 **Service 层** 统一做「是否为成员、是否为 owner/admin、visibility 是否允许当前用户」等检查，禁止访问时抛 `ForbiddenException`（FORBIDDEN），不依赖前端隐藏按钮。

**建议**：在实现计划的「API 设计」表中为每个接口注明「Auth：JWT / @Public」及「权限规则（例：仅 owner/admin 可 PATCH/DELETE）」；在「实施顺序」中明确「所有写操作与敏感读操作在 Service 内做角色与可见性校验」。

---

#### （2）审计（AuditLog）

- **现状**：组队文档未提及审计。
- **企业级要求**：参考学校 update 与 auth 的 [AuditLogService](apps/api/src/common/services/audit-log.service.ts) 用法，关键操作需可追溯。

**建议**：在计划中增加「审计」小节：

- **可选方案 A**：扩展 `AuditAction`（如 `TEAM_CREATE`、`TEAM_DISBAND`、`TEAM_INVITE`、`TEAM_MEMBER_REMOVE`），便于筛选与报表。
- **可选方案 B**：复用 `ADMIN_ACTION` 仅用于管理员操作；用户操作用统一 action（如 `USER_ACTION`）且 `resource: 'teams'`，`metadata: { action: 'create'|'disband'|'invite'|'leave'|'kick', teamId, ... }`。
- **必记操作**：创建队伍、解散队伍、邀请（成功）、踢人、转移 owner；`resource: 'teams'`，`resourceId: teamId`，metadata 中不记录 PII，仅必要业务字段（如 action、inviteeId 是否记录需合规评估）。

---

#### （3）错误码与异常

- **现状**：设计报告有用户侧文案（如「队伍已满」「邀请已失效」），未与后端错误码对应。
- **企业级要求**：与 [ADR-0006](docs/adr/0006-prisma-exception-handling-strategy.md) 及全局 Filter 一致，使用标准 code，便于前端统一处理与 i18n。

**建议**：在计划中增加「错误码约定」表，例如：

| 场景                                        | HTTP       | error.code                  | 说明                          |
| ------------------------------------------- | ---------- | --------------------------- | ----------------------------- |
| 队伍不存在                                  | 404        | NOT_FOUND                   | P2025 或业务校验              |
| 无权限（非成员访问 PRIVATE、非 owner 操作） | 403        | FORBIDDEN                   | Service 抛 ForbiddenException |
| 已加入/已申请/重复邀请                      | 409        | CONFLICT 或 DUPLICATE_ENTRY | 业务校验                      |
| 队伍已满                                    | 400 或 409 | BAD_REQUEST / CONFLICT      | 业务校验                      |
| 邀请过期或 token 无效                       | 400 或 404 | BAD_REQUEST / NOT_FOUND     | 业务校验                      |
| 参数校验失败                                | 400        | BAD_REQUEST                 | DTO + class-validator         |

并说明：Prisma 唯一约束冲突（如同一用户重复加入）映射为 409 DUPLICATE_ENTRY；前端根据 `error.code` 展示 `teams.errors.*` 文案。

---

#### （4）DTO 与输入校验

- **现状**：计划中有 CreateTeamDto 字段建议，未写校验规则。
- **企业级要求**：与学校等模块一致，使用 class-validator；[SanitizeInterceptor](CLAUDE.md) 已全局 strip HTML，仍需限制长度与枚举。

**建议**：在计划中写明：

- **CreateTeamDto / UpdateTeamDto**：`name` @IsString() @MinLength(1) @MaxLength(100)；`description` @IsOptional() @MaxLength(500)；`visibility` @IsEnum(TeamVisibility)；`joinPolicy` @IsEnum(TeamJoinPolicy)；`maxMembers` @IsOptional() @IsInt() @Min(2) @Max(100)；`schoolId` @IsOptional() @IsUUID()；`tags` @IsOptional() @IsArray() @ArrayMaxSize(10) 等。
- **邀请/申请**：message @IsOptional() @MaxLength(200)。
- 不记录完整 body 到审计；仅 metadata 中必要字段。

---

#### （5）前端路由保护（middleware）

- **现状**：设计报告要求「游客可看发现列表与详情，加入/创建需登录」，未说明与 [middleware.ts](apps/web/src/middleware.ts) 的配合。
- **企业级要求**：PROTECTED_PATTERNS 决定哪些路径未登录即重定向；需与「游客可访问 /teams」一致。

**建议**：在计划中明确：

- **不**将 `/teams` 加入 PROTECTED_PATTERNS，以便游客访问 `/teams` 及 `/teams/[id]`（公开队伍）。
- 创建、加入、我的队伍等「需登录操作」由 **前端** 在点击时检查登录态：未登录则跳转 `login?callbackUrl=/teams/create`（或当前页）；**后端** 对需认证接口返回 401，前端 apiClient 统一处理 401 并跳转登录。
- 若后续需要「仅登录用户可进 /teams 页面」（即整页保护），再考虑将 `/teams` 加入 PROTECTED_PATTERNS 并改为「发现」接口在未登录时返回精简列表或 401 由前端展示「登录后查看」。

---

#### （6）Admin 与运营

- **现状**：组队文档未涉及管理员对队伍的管理。
- **企业级要求**：参考 Admin 学校、用户管理等，重要资源通常具备「列表 + 详情 + 强制操作」能力，便于合规与风控。

**建议**（可选，可作为 v1 或 v2）：

- **Admin API**：`GET /admin/teams`（分页、筛选）、`GET /admin/teams/:id`、`DELETE /admin/teams/:id`（强制解散）；仅 `@Roles(Role.ADMIN)`。
- **审计**：管理员解散记 `AuditAction.ADMIN_ACTION`，`resource: 'teams'`，`resourceId: id`，`metadata: { action: 'admin_disband', reason?: string }`。
- **前端**：Admin 下新增「组队管理」页或 Tab，列表 + 操作（查看/解散）；i18n 使用 `admin.teams.*`。

---

#### （7）测试与质量

- **现状**：计划中有实施顺序，未提单测。
- **企业级要求**：与现有模块一致，新模块需可测且 mock 依赖。

**建议**：在实施顺序中增加：

- **TeamService**：`team.service.spec.ts` — 创建、加入、离开、解散、邀请、权限（非成员访问、非 owner 修改）等用例；mock PrismaService、必要时 AuditLogService。
- **TeamController**：`team.controller.spec.ts` — 各端点调用 service 并传参正确；mock TeamService、CurrentUser；公开/需 JWT 的端点区分。
- 若引入 AuditLogService，在 spec 中 mock 并断言 log 调用参数（action、resource、resourceId）。

---

#### （8）缓存与性能

- **现状**：未提及缓存。
- **企业级要求**：学校等模块在写后失效缓存；组队若列表/详情 QPS 高，可后续加 Redis。

**建议**：v1 可不实现缓存，在计划中注明「列表与详情接口暂不缓存；若后续性能需求明确，再对 GET /teams、GET /teams/:id 做短 TTL Redis 缓存，并在创建/更新/解散/加入/离开时失效相关 key」。避免首版过度设计。

---

#### （9）限流与防滥用

- **现状**：仅依赖全局 ThrottlerGuard（100/60s per IP）。
- **企业级要求**：学校批量 Logo 填充有「每校间隔 + 单次 limit」；组队可对「创建队伍、发送邀请」等做更严限制（按用户维度）。

**建议**：v1 可仅依赖全局限流；在计划中注明「若运营中发现滥用，可对 POST /teams、POST /teams/:id/invite 等增加 per-user 限流（如 10 次/小时）」，由 ThrottlerGuard 的 limit 或自定义 Guard 实现。

## 四、结论与下一步

- **结论**：组队的产品与 UX/UI 设计（用户流、IA、边界、i18n、组件与设计系统对接）已基本达到企业级表述；**后端与平台化维度**（认证鉴权、审计、错误码、DTO、路由保护、测试、可选 Admin/缓存/限流）在现有文档中缺失或未显式对齐项目标准，需在**实现计划**中补全上述小节与表格。
- **建议**：将本分析中的「建议」逐条并入组队实现计划（或单独「企业级检查清单」），在开发前评审通过后再实施；实施时优先做鉴权、审计、错误码与 DTO，再按现有设计报告做前端与联调。

完成以上补充后，组队方案即可视为符合当前项目定义的企业级标准。
